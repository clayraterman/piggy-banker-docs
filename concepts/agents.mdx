# Agents: repeatable finance workflows

Agents turn a well-defined finance process into a versioned, client-scoped workflow. Their durable lifecycle is:

```text
Agent template → immutable revision → client deployment → run
```

## Template

The template defines reusable workflow intent: what the agent should do, what evidence it needs, expected output, and available configuration.

## Revision

Publishing creates an immutable revision. Live behavior is never silently changed by editing an already-published definition.

## Deployment

A deployment applies one revision to one client. It resolves:

- enabled state,
- schedule,
- destinations,
- relevant Context,
- approval posture,
- skills,
- and client-specific overrides.

Client defaults such as a Slack channel, reporting style, Context pack, or approval policy can come from workspace defaults. A deployment can inherit or explicitly override them.

## Run

A run records the exact revision and resolved configuration used for that execution. It also retains inputs, tool activity, results, evidence, artifacts, approvals, tasks, and events.

This makes the answer to “why did the agent do that?” inspectable.

An in-app report artifact remains operator-side. Publishing a report to the client portal is a separate action that creates a published report; Slack approval or delivery does not publish it.

## Run modes

| Mode | Behavior |
| --- | --- |
| **Manual test** | Produces an in-app, reviewable artifact; creates no tasks, approvals, or external deliveries |
| **Manual live run** | Uses the queued production path and configured action controls |
| **Scheduled run** | Enters the queue at an eligible schedule slot after readiness checks |

## Data access

Agents read approved, client-scoped finance sources, saved metrics, series, Context, and skills. They do not receive raw database access or permission to cross client boundaries.

The target product will let Page composition inform reporting workflows. Today, agents consume the underlying finance and metric primitives rather than a rendered Page object.

## Controlled side effects

An agent can propose an external action. Proposal, human decision, queued dispatch, and provider delivery are separate states. Approval is not proof that a message was delivered.

<Note>
  A schedule is not a substitute for readiness. Required data, destination configuration, and policy checks must pass before scheduled work can proceed.
</Note>
